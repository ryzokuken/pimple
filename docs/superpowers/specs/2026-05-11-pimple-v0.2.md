# pimple — design (v0.2)

**Status**: draft 2026-05-11
**Scope**: extend the v0.1 vdir-backed calendar client with edit, delete, month view, configurable week start, AppConfig persistence, and a first-run vdir-root picker. Preserves every architectural invariant of v0.1.

## 1. Background

v0.1 ships a polished, read-and-create week-view calendar. v0.2 closes three gaps that block daily use:

1. **Round-trip editing.** Users need to edit and delete events. The v0.1 architecture has been shaped for this: `raw_ics` is preserved on every parse, the write path is symmetric for create/update/delete (each is "atomically replace a file in a vdir"), and the watcher is the single source of truth so we never need separate "internal" vs "external" change paths.
2. **Recurring-event semantics.** Edit and delete of recurring events are not a single operation but three: *this instance / this and future / all*. The data model already supports it (`overrides: Vec<OverrideInstance>`, `exdates: Vec<EventTime>`); v0.2 adds the write-side counterparts and the UI to choose between them.
3. **Bootstrap UX.** v0.1's "open the JS console and call `set_vdir_root`" workflow is acceptable for a developer alpha but blocks real users. v0.2 adds a first-run dialog and a persisted config file so the choice survives restart.

Guiding values, unchanged from v0.1:

- **Minimalism** — every feature here is forced by user need. Nothing speculative.
- **Standards-first** — RFC 5545 §3.8.5 for recurrence semantics, RFC 5545 §3.8.4.4 for `RECURRENCE-ID` overrides, RFC 9557 for IPC timestamps, XDG Base Directory Specification for AppConfig location.
- **Local / privacy-conscious** — no new network code. Same architectural posture as v0.1.
- **Cross-platform** — Linux, macOS, Windows. Mobile still preserved as a v0.3+ target.
- **Compiled top to bottom** — same stack: Rust + Svelte 5 compiled output.

## 2. Scope

### In scope for v0.2

- **Edit events** — title, description, location, time range (all-day toggle), collection, RRULE. Round-trip preserves unknown properties (VALARM, X-vendor) through `raw_ics`-patch.
- **Delete events** — single non-recurring, plus three recurring modes.
- **Recurring edit/delete semantics** — *this instance*, *this and future*, *all*.
- **Month view** — calendar grid with one row per week, events as chips. Same data layer; no new IPC.
- **Configurable week start** — Monday or Sunday. Persisted in AppConfig.
- **First-run vdir-root picker** — file dialog on first launch with no configured vdir.
- **AppConfig persistence** — XDG-compliant config file storing vdir root, week start, and per-collection visibility.
- **Window geometry persistence** — width/height/x/y restored on launch.
- **Concurrent-write detection** — if pimsync (or another writer) overwrites a file between modal-open and save, surface a non-destructive conflict and offer to reload.

### Deferred to v0.3

- **VTODO (tasks)**, **vCard (contacts)**.
- **Natural-language quick event entry**.
- **Reminders and desktop notifications**.
- **Mobile platforms via Tauri 2**.
- **iTIP file-association import** ("open with pimple" for an `.ics` invite).
- **Free/busy view** across collections.
- **Search**.

### Explicit non-goals (v0.2)

- No CalDAV sync logic in pimple. pimsync still owns all network I/O.
- No writing to vdir collection metadata (`color`, `displayname`).
- No invocation or supervision of pimsync.
- No RDATE handling. Inputs with RDATE will continue to silently drop the RDATE list during parse, as in v0.1. (Adding RDATE doesn't block edit/delete.)
- No `RANGE=THISANDFUTURE` *reading*. Files that ship a RECURRENCE-ID with RANGE=THISANDFUTURE will be treated as single-instance overrides on parse — same as v0.1. *Writing* this-and-future edits uses the master-split strategy (§4.3), not the RANGE parameter.
- No VTIMEZONE block parsing. Pimple continues to interpret `TZID=America/New_York` directly against IANA tzdb.

## 3. Architecture

No new crates. Existing layer responsibilities are preserved:

- `pimple-core` gains an `update_event` + `delete_event` write path, an `AppConfig` persistence module, and conflict-detection wiring on the write path.
- `pimple-tauri` gains four new commands plus the first-run flow.
- `frontend/` gains a month view, an edit modal (refactored shared component with the create modal), a recurring-edit decision dialog, a first-run wizard, and settings persistence.

### Data flow for edit (push-based, identical shape to v0.1 create)

```
EventModal (edit mode) submits
  → invoke("update_event", { uid, request, expected_raw_hash })
  → pimple-core::write::update_event
    → load current .ics; hash; compare to expected_raw_hash
    → if mismatch: return CoreError::Conflict — UI shows conflict toast
    → if match: build new .ics via raw_ics-patch; atomic temp-file + rename
  → notify watcher → debounce → parse → IndexChange::Upsert
  → broadcast → forwarder → Tauri events_changed
  → events store → re-query → re-render
```

The write path **still never touches the index directly**. Every edit goes through the watcher pipeline.

### Concurrent-write detection (the v0.2 new invariant)

When the user opens an event for edit, the modal records the hash of the current `raw_ics`. On submit, the write path re-reads the file, hashes again, and refuses to overwrite if the hash has changed. The user sees a conflict toast: *"This event was modified externally. Reload?"* On reload, the modal re-fetches; their edits are lost (they can re-apply manually). This favors safety over convenience and matches how `git rebase`-style conflicts are surfaced.

Hash is SHA-256 of the raw `.ics` bytes (32 bytes — negligible storage, ~10µs at parse time). Stored in `Event` as `raw_hash: [u8; 32]` and serialized to the frontend as a hex string.

## 4. Data model

### 4.1 Additions to `Event`

```rust
struct Event {
    // ... v0.1 fields ...

    /// SHA-256 of `raw_ics`. Used for optimistic concurrency on update/delete.
    raw_hash: [u8; 32],   // serialized as 64-char hex string at the IPC boundary
}
```

The frontend treats `raw_hash` as opaque. It is passed back to `update_event` and `delete_event` to detect concurrent writes.

### 4.2 New types

```rust
/// User-supplied data for editing an event.
struct UpdateEventRequest {
    uid: String,
    expected_raw_hash: String,     // hex
    summary: String,
    description: Option<String>,
    location: Option<String>,
    start: EventTime,
    end: EventTime,
    rrule: Option<RRuleSpec>,
    /// Which recurring scope the edit applies to. Ignored for non-recurring events.
    recurring_scope: RecurringScope,
}

/// User-supplied data for deleting an event.
struct DeleteEventRequest {
    uid: String,
    expected_raw_hash: String,
    /// Which recurring scope the delete applies to. For non-recurring events,
    /// `All` is the only valid value; the backend errors otherwise.
    recurring_scope: RecurringScope,
    /// For `ThisInstance` / `ThisAndFuture`, identifies which occurrence.
    /// Ignored for `All`.
    occurrence_recurrence_id: Option<EventTime>,
}

enum RecurringScope {
    ThisInstance,
    ThisAndFuture,
    All,
}
```

### 4.3 The three recurring modes — concrete operations

| Scope | Edit | Delete |
|---|---|---|
| **ThisInstance** | Append a new VEVENT to the file with `RECURRENCE-ID=<occurrence>` and the edited fields | Append the occurrence's start time to the master VEVENT's `EXDATE` |
| **ThisAndFuture** | Truncate master with `UNTIL=<occurrence - 1ns>` in its RRULE; write a **new** `.ics` file with a fresh UID, DTSTART at the occurrence, the requested fields, and the same RRULE pattern | Truncate master with `UNTIL=<occurrence - 1ns>`; drop any overrides whose RECURRENCE-ID is ≥ occurrence |
| **All** | Mutate master VEVENT in place; drop overrides that no longer make sense (those whose recurrence-id falls outside the new pattern) | Remove the entire `.ics` file |

**UID continuity** on `ThisAndFuture` edit: the continuation gets a **new UID**. Rationale: (1) RFC 5545 is silent on this; (2) Google Calendar issues a new UID, Apple keeps the old one — there is no universal correct answer; (3) a new UID gives a clean "one UID = one file = one logical series" invariant for storage. pimsync handles either model upstream.

### 4.4 AppConfig (extended)

```rust
struct AppConfig {
    vdir_root: Option<PathBuf>,     // was: PathBuf — None until first-run picker resolves
    collection_visibility: HashMap<String, bool>,
    week_start: WeekStart,
    window_geometry: Option<WindowGeometry>,
}

struct WindowGeometry {
    width: u32,
    height: u32,
    x: i32,
    y: i32,
}
```

Persisted as TOML at:

- Linux: `$XDG_CONFIG_HOME/pimple/config.toml` (default `~/.config/pimple/config.toml`)
- macOS: `~/Library/Application Support/dev.ryzokuken.pimple/config.toml`
- Windows: `%APPDATA%\dev.ryzokuken.pimple\config.toml`

Resolved via the `dirs` crate (already in the dependency tree's transitive closure via Tauri).

## 5. `pimple-core` internals

### 5.1 New module: `config_store`

`load() -> AppConfig` (returns defaults on missing file) and `save(&AppConfig) -> Result<()>` (atomic via temp-file + rename). Path resolution via `dirs::config_dir()`. Migration-friendly: unknown TOML fields are ignored on load; missing fields take defaults.

### 5.2 Extended `write` module

```rust
pub async fn update_event(
    collection_path: &Path,
    uid: &str,
    expected_raw_hash: &[u8; 32],
    req: &UpdateEventRequest,
) -> Result<()>;

pub async fn delete_event(
    collection_path: &Path,
    uid: &str,
    expected_raw_hash: &[u8; 32],
    req: &DeleteEventRequest,
) -> Result<()>;
```

Each:

1. Read `<collection>/<uid>.ics` into memory.
2. Hash and compare against `expected_raw_hash`. Mismatch → `CoreError::Conflict`.
3. Apply the scope-appropriate transformation (§4.3).
4. Atomic temp-file + rename to commit. For *ThisAndFuture* edit, this is **two** atomic operations: the master rewrite and the continuation file write. Order: write the continuation first (failure leaves the master intact; user retries), then the master truncation.

For deletes that remove the entire file (`Scope::All` on non-recurring or fully-deleted recurring), use atomic `rename` to a tempfile, then `remove_file`. This survives a crash between the two with no data loss — at worst the file ends up renamed but not deleted, and pimsync will pick it up on next sync.

### 5.3 Extended `ical::build`

A new function `patch_ics(raw: &str, mutation: IcsMutation) -> Result<String>` that takes the original `.ics` and a structured mutation (set-summary, add-exdate, replace-vevent-with-recurrence-id, etc.) and produces a new `.ics`. Preserves unknown properties (VALARM, X-vendor, ATTENDEE, etc.) by parsing the original into a tree, mutating the relevant nodes, and re-serializing — *not* by regenerating from `Event` (which would drop everything `Event` doesn't model).

This is the data-loss-defense load-bearing piece. Its tests run round-trips against the full v0.1 fixture corpus and assert no unknown property is dropped.

### 5.4 New errors

```rust
enum CoreError {
    // ... v0.1 variants ...
    Conflict { uid: String, message: String },
    InvalidScope { reason: String },   // e.g. ThisInstance on a non-recurring event
}
```

`Conflict` maps to `IpcError::Conflict` and renders as a non-destructive toast (with "Reload" action).

## 6. `pimple-tauri` bridge

Four new commands:

- `get_config() -> AppConfig`
- `set_config(AppConfig) -> Result<()>`
- `update_event(UpdateEventRequest) -> Result<()>`
- `delete_event(DeleteEventRequest) -> Result<()>`
- `pick_vdir_root() -> Option<PathBuf>` — opens the OS file picker via `@tauri-apps/plugin-dialog`

A startup hook reads `AppConfig`, and if `vdir_root` is `Some(path)`, calls `set_vdir_root` internally. The first-run flow lives in the frontend.

A second startup hook persists the window geometry on close (via Tauri's `WindowEvent::CloseRequested`).

### Edit modal

The existing `EventModal` becomes mode-aware. Prop: `mode: "create" | "edit"`, plus optional `event: EventInstance` when editing. On open in edit mode, the modal pre-fills from the instance, records the source event's `raw_hash`, and on submit calls `updateEvent`. If the underlying event is recurring, submit first opens the `RecurringScopeDialog` to pick scope.

### Delete flow

A delete button on the modal (edit mode only). On click: if non-recurring, confirm and call `deleteEvent` with `Scope::All`. If recurring, open `RecurringScopeDialog` first.

### Month view

CSS Grid: 7 columns × N rows (N = 5 or 6 depending on which month). Each cell shows day number, a small color-dotted strip of up to 3 event chips, and "+ N more" for overflow. Clicking a chip opens the edit modal; clicking empty space opens the create modal pre-filled with that day. No overlap-layout algorithm needed; events stack vertically as chips.

### First-run picker

A blocking dialog on app start if `AppConfig.vdir_root` is `None`. Calls `pickVdirRoot`, persists the result via `setConfig`, then proceeds to the main UI.

## 8. Error handling

The three v0.1 classes plus one new:

4. **Conflict errors** (concurrent write detected). Surfaced as a `ConflictToast` with a "Reload" button. Not dismissible without resolution. Bypassing it is impossible — the data hash diverged, and any save without reload would clobber the external write.

Other errors keep their v0.1 handling.

## 9. Testing strategy

Additions on top of v0.1's matrix.

`pimple-core`:

- Fixtures for **recurring edit/delete in each of the three modes**, including the master-split shape for `ThisAndFuture`. Per mode: a `before.ics` and an `after.ics`; the test parses `before`, applies the mutation, asserts the output equals `after` byte-for-byte (modulo DTSTAMP/LAST-MODIFIED).
- **Conflict-detection unit tests**: create a fixture, hash it, modify it on disk, call `update_event` with the original hash → assert `CoreError::Conflict`.
- **Round-trip preservation property test**: take every `.ics` in `tests/fixtures/ics/`, apply a no-op summary edit, assert the resulting parse equals the original parse modulo `summary`. Specifically asserts that VALARM and X-vendor properties survive.
- **AppConfig persistence**: write a config, kill the process, read it back; assert all fields match.
- **No new mocks**. Real `tempdir` filesystems.

`pimple-tauri`:

- Integration tests for `update_event` (success and conflict paths), `delete_event` (each scope), `get_config`/`set_config` round trip.

Frontend:

- Vitest for `RecurringScopeDialog` choice → IPC argument mapping.
- Vitest for `MonthGrid` cell-event-bucketing logic.
- Playwright E2E:
  - Smoke test: create → edit → assert update visible.
  - Recurring smoke: create a weekly event → delete one instance → assert the rest survive.
  - First-run smoke: launch with no config → assert picker appears.

CI matrix unchanged. New tests are additive.

## 10. Delivery phasing

v0.2 ships in 8 task groups, each landing as its own atomic commit-set:

1. **AppConfig persistence** (config_store module, TOML schema, get/set commands)
2. **First-run picker** (frontend wizard, blocking dialog, persist on resolve)
3. **Configurable week start** (plumbing `WeekStart` from store to grids; navigator preference toggle)
4. **`raw_ics`-patch core** (the `patch_ics` function + round-trip preservation property test)
5. **Delete** (all three scopes, conflict detection, IPC command, modal button)
6. **Edit** (all three scopes, conflict detection, IPC command, modal mode refactor)
7. **Month view** (MonthGrid component, EventChip, view toggle, view store)
8. **Window geometry persistence** (Tauri WindowEvent hook, AppConfig field)

The v0.2 implementation plan decomposes each group into TDD-shaped tasks.

## 11. Open questions

- **Default vdir root suggestion in the first-run picker**: pre-select `~/.calendars` if it exists? Or always require an explicit user choice? Leaning toward "pre-fill but allow override."
- **What happens to an in-flight modal when the watcher fires a Remove for the same UID?** Likely: surface a "this event was deleted externally" message, close the modal, no save.
- **Icon design**. v0.1 ships with no real icons (gitignored, regenerated locally via `just icons-dev` for placeholders). v0.2 should ship designed icons for all platforms. Not blocking the work itself.
